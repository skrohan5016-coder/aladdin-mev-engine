# F3 Acceptance Contract

F3 is accepted only when one exact head and its current synthetic merge satisfy all requirements below.

## Required implementation

- exact accepted F2 parent identity;
- code-hash, layout, fee, arithmetic, and assumption-bound models;
- conflicting models for one code hash rejected;
- token identity and reserves decoded from authenticated storage evidence;
- exact-snapshot pool universes;
- deterministic two-to-four-hop simple cycles without pool reuse;
- checked arithmetic, packed capacity, and exact per-hop floor;
- continuous mathematics used only as an optimistic bound;
- bounded deterministic exact optimization with smaller-input tie-breaking;
- aggregate route-search work bounded before optimization begins;
- incomplete or nonpositive results denied opportunity authority;
- opportunity evidence recomputes optimization and quote;
- intermediate quote and optimization objects grant no standalone opportunity authority;
- gross-only, execution-ineligible output labels;
- exact ten-file F3 schema lock.

## Required adversarial validation

Wrong chain, address, code hash, token, slot, reserve, anchor, model, route, arithmetic domain, optimizer status, or evidence identity must fail closed. Randomized two-, three-, and four-hop optimizations must match exhaustive exact search. Continuous interval bounds must never understate discrete continuous profit. All inherited F0–F2 tests must remain green.

## Required CI

Exact source head and current synthetic merge must independently pass compile, full tests, repository policy, architecture lock, source-contract lock, F2 schema lock, F3 schema lock, and clean-worktree checks with read-only permissions and immutable action pins.

F3 acceptance does not authorize production models, networking, credentials, EVM execution, gas/inclusion/net-profit claims, funding, keys, signing, transaction construction, bundle submission, deployment, or trading.

## Final authority hardening


- The canonical empty-code hash cannot be registered as a pool runtime model.
- Optimization result counters, bounds, and status-specific winner fields are cross-validated.
- Route and optimizer input ceilings are closed to exact uint256 values.
- A budget-exhausted result is incomplete and cannot carry a winning input, output, or profit.
- Continuous pruning bounds are themselves bounded to uint256 and remain non-authoritative.
